\section{Introduction}

Search-based machine-learning (ML) agents frame ML engineering tasks as a search over executable candidate programs. Each program embodies choices about data processing, model architecture, and training configuration. The agent proposes a program, runs it, inspects the resulting feedback, and uses that evidence to guide subsequent revisions \citep{jiang2025aide,lee2026forecritic}.

Execution gives the agent evidence about a candidate: errors reveal implementation failures, while validation scores indicate its measured performance. In AIDE, this feedback guides the expansion of a tree of candidate programs \citep{jiang2025aide}. Obtaining that evidence can require hours of model training and evaluation on MLE-bench tasks \citep{chan2024mle,lee2026forecritic}. With limited GPU and wall-clock time, an agent can test only a fraction of its proposed programs; time spent on candidates later discarded leaves fewer opportunities to explore other ideas \citep{lee2026forecritic}.

ForeAgent reduces this cost by using an LLM to compare candidate revisions before execution. Within AIDE's improvement stage, its Predict-then-Verify loop proposes multiple programs, predicts their relative performance through pairwise judgments, and executes selected candidates \citep{zheng2026predict}. Across five MLE-bench tasks, the authors report 3.2 times as many explored nodes, a 6-fold speedup in reaching peak performance, and an approximately 6\% relative gain in average Beat Ratio over AIDE. The benefit depends on reliable predictions: on the paper's pairwise corpus, the LLM judge selects the execution-labeled winner in 61.5\% of comparisons, so errors can remove promising revisions before they are verified \citep{zheng2026predict}. More recent work, ForeCritic, trains a reward model on execution-labeled program pairs and uses it in place of ForeAgent's LLM judge while retaining its pairwise selection loop \citep{lee2026forecritic}.

These outcome-labeled comparisons establish which completed program performed better, but provide no direct supervision about the quality of the modification that produced it. Process errors in ML work include unsound validation, data leakage, and revisions that fail to address an observed problem; AdaPRA demonstrates that rubric-guided review of agent trajectories and artifacts can identify such errors \citep{naik2026adapra}. This proposal studies a different use of process feedback: scoring a proposed revision \emph{before} executing it. We ask whether a process-quality reward model, given a parent program, its observed feedback, and a proposed child, can improve ForeAgent's candidate selection and final task performance under the same GPU and wall-clock budget. ForeCritic provides the direct outcome-supervised comparison, while ForeAgent's generator, search tree, and execution rules remain fixed.

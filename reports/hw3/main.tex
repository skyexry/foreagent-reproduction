\section{Introduction}

LLM-based machine learning (ML) agents automate model development by searching over candidate solutions through iterative cycles of code generation, execution, and refinement. Although agents can propose candidates quickly and cheaply, evaluating each one requires computationally expensive training and validation \citep{jiang2025aide,zheng2026predict}. This asymmetry limits how many experiments an agent can run within a fixed budget, so the quality of its search decisions matters for both resource efficiency and final performance. Poor decisions are costly in two ways. In terms of efficiency, repeated failures and revisions that bring only marginal gains consume time and compute, delaying progress toward a target level of performance. In terms of solution quality, fixating on a narrow family of approaches or continuing to refine a stalled solution can keep the agent from finding stronger alternatives before its budget runs out. These challenges raise a broader question: how can ML agents learn from past experiments to improve how they generate candidates, assess alternatives, and choose subsequent search directions?

AIDE \citep{jiang2025aide} structures this search as a tree whose nodes contain candidate programs and their execution results. Drafting, debugging, and improvement operators expand the tree, while a search policy determines which node to develop next. Summaries of previous attempts provide context for subsequent code generation, allowing the agent to build on promising solutions and repair unsuccessful attempts. However, each new candidate must be executed before its measured performance can inform further search. Consequently, the cost of training and validation constrains how broadly the agent can explore.

ForeAgent \citep{zheng2026predict} builds directly on AIDE's architecture and addresses this bottleneck by redesigning the improvement stage. It generates multiple candidate solutions and uses an LLM to compare their expected performance based on their code, the task description, and a verified data analysis report. Confidence-gated comparisons filter the candidates before selected solutions are executed. This \emph{predict-then-verify} workflow allows the agent to consider more alternatives without training every candidate, while retaining real execution feedback to verify progress. In the authors' evaluation on five MLE-bench tasks, ForeAgent explored more candidates and reached peak performance faster than AIDE. These results demonstrate the promise of predictive selection for improving search efficiency.

Subsequent work seeks more informative and reliable evidence for predictive decisions. MLE-World \citep{ko2026mleworld} predicts execution outputs, including errors, training logs, and validation scores, and uses them to support both candidate selection and code revision. Its pairwise selection strategy extends ForeAgent by incorporating predicted terminal outputs into candidate comparisons. ForeCritic \citep{lee2026forecritic} takes a training-based approach, learning preferences from executed program pairs to directly predict which candidate will perform better. The authors evaluate this selector within AIDE, ML-Master, and ForeAgent. Rehearse \citep{ji2026rehearse} instead retrieves similar modifications and their observed outcomes from the current task to inform comparisons between new proposals, then adds subsequent execution results to its memory. These methods ground selection in predicted execution feedback, outcome-supervised preferences, or relevant historical evidence.

A separate line of work makes the agent's own operating procedures a target for improvement. Inspired by recursive self-improvement (RSI), \emph{harness evolution} updates the prompts, reusable skills, memory mechanisms, and control logic surrounding an LLM. AIDE$^2$ \citep{srikanth2026aide2} implements an outer optimization loop that modifies a research agent's code, evaluates the resulting versions on a task suite, and retains changes that improve performance under fixed evaluation budgets. Its discovered modifications include search policies and context-management mechanisms. Evo-Harness \citep{wei2026evoharness} instead adapts through reusable guidance: it converts execution experience into skills and updates the external harness across tasks while keeping the underlying model frozen. These studies provide empirical support for improving agent behavior through changes to its harness.

Applying harness evolution to predictive search introduces a specific challenge: candidate generation, predictive selection, and execution feedback jointly determine which experiments the agent observes and learns from. Changes to the generator alter the candidates presented to the selector, while changes to the selector alter which candidates receive execution feedback. An improvement to any individual component must therefore be evaluated by its effect on the full search process. AIDE$^2$ evolves an AIDE-based search driven by execution feedback; its reported design does not include ForeAgent's pre-execution predictive filter \citep[Sections~2.2 and~3.5]{srikanth2026aide2}. ForeAgent introduces this additional selection stage while retaining predefined comparison prompts and selection rules \citep{zheng2026predict,foreagentcode}. This makes ForeAgent a natural testbed for studying how experience-driven updates to the harness affect both the quality of search decisions and the resources required to make them.

This proposal therefore asks: \textbf{Can harness evolution make machine learning agents search more efficiently?} Using ForeAgent as the baseline, the following sections explain its predict-then-verify workflow and present a reproduction that includes candidate generation, experiment selection, and actual model training and validation. The end-to-end run provides the foundation for studying adaptations to individual components and their interactions. Planned evaluations will assess whether evolved harnesses find better solutions within a fixed total budget or reach comparable solution quality with fewer resources, with the cost of harness adaptation counted toward the total budget.

\section{Baseline Explanation: ForeAgent}
\label{sec:baseline}

\subsection{Task and optimization objective}

ForeAgent is an LLM-based system for autonomously developing machine learning solutions \citep{zheng2026predict}. Its input consists of a task description, a dataset, an evaluation metric, and a computational budget. Its output is a candidate program and the predictions produced by the selected solution. The program specifies a complete modeling pipeline, including data preprocessing, feature construction, model choice, training, validation, and inference. Search therefore operates over executable solutions whose modeling choices can change across iterations.

Let $I$ denote the task description, $D$ the dataset, and $C$ a candidate program. Executing $C$ produces runtime observations and a validation metric $M(C)$. Define $u(C)=M(C)$ for a maximized metric and $u(C)=-M(C)$ for a minimized metric. A search policy $\pi$ determines which programs to generate and execute. Its budgeted objective can be expressed as
\begin{equation}
 \max_{\pi}\;\mathbb{E}\!\left[\max_{C\in\mathcal{E}_{\pi}(B)}u(C)\right],
 \label{eq:objective}
\end{equation}
where $\mathcal{E}_{\pi}(B)$ contains the valid programs evaluated within budget $B$. This formulation describes the search objective: both the quality of proposed programs and the allocation of evaluation resources determine the best solution discovered. Validation feedback guides development, and the private test set evaluates the final submission.

\subsection{Foundation: AIDE's search over programs}

ForeAgent builds directly on AIDE's tree-based search architecture \citep{jiang2025aide,zheng2026predict}. Each node represents a candidate program, and a parent--child edge records a revision of an earlier solution. A journal stores the code, parent identity, execution status, runtime output, and extracted validation metric. This representation retains multiple development paths and connects each new revision to the evidence that motivated it.

Three operators expand the search tree. \emph{Drafting} generates an initial solution from the task and data context, providing starting points for exploration. \emph{Debugging} repairs an unsuccessful program using its code and execution errors. \emph{Improvement} develops a valid solution using its existing implementation, performance, and the history of previous attempts. A controller selects the operator and parent node. In the released configuration, the agent first creates three drafts, prioritizes eligible debugging with probability 1.0 up to a debugging depth of 20, and otherwise improves the best valid node \citep{foreagentcode}.

The generator receives summaries of prior attempts so that subsequent programs can incorporate earlier observations. After execution, a feedback model extracts success or failure information and the reported validation metric from the runtime output. The journal then supplies updated context for the next decision. AIDE thus combines code generation, tool execution, persistent history, and feedback-guided refinement in one search loop. Obtaining a new measured score requires executing the corresponding program, which makes training and validation a central resource cost.

\subsection{ForeAgent's extension: predict before execution}

ForeAgent separates proposing an improvement from committing resources to evaluate it. For a selected parent solution, the agent generates several alternative programs and compares their expected performance using the task description, dataset analysis, and candidate code. The comparison results determine which candidates proceed to training and validation. Their observed outcomes are then added to the search history, providing evidence for subsequent debugging and improvement. This design allows the agent to consider a broader set of revisions while concentrating execution resources on selected candidates \citep{zheng2026predict}.

\paragraph{Generating alternatives.}
ForeAgent introduces predictive filtering in the improvement branch; drafting and debugging retain direct execution. An improvement step generates $m=10$ candidates from the selected parent. Each candidate contains an improvement plan and its code implementation. The generator uses the parent solution and journal summary, while previously generated plans within the batch provide context for proposing alternatives. The resulting batch is the input to predictive selection.

\paragraph{Grounding predictions in data.}
The comparison model receives a textual data analysis report in addition to the task description and programs. The paper constructs this report through a Profile--Verify--Verbalize pipeline: profiling code analyzes the dataset, verification checks the resulting observations, and verbalization converts the verified findings into a report \citep{zheng2026predict}. The task description specifies the prediction objective and evaluation requirements; the report supplies dataset properties; and the programs expose the modeling and training choices being compared. Together, these inputs allow the predictor to assess how well each proposed pipeline fits the task. The reproduction uses the released task report.

\paragraph{Predicting relative performance.}
For programs $C_i$ and $C_j$, the comparison LLM returns reasoning, a preferred candidate, and confidence:
\begin{equation}
 (z_{ij},\widehat y_{ij},c_{ij})
 =f_{\theta}(I,D_{\mathrm{rep}},C_i,C_j;P).
 \label{eq:predictor}
\end{equation}
Here $D_{\mathrm{rep}}$ denotes the data report, $P$ the comparison prompt, $z_{ij}$ the reasoning, $\widehat y_{ij}$ the relative preference, and $c_{ij}$ the self-reported confidence. This produces an estimate of which program will perform better before its new training outcome is available. ForeAgent uses pretrained models with fixed parameters. Its agent-level method is therefore defined by inference-time decision rules; task models are trained when selected candidate programs execute.

\subsection{Selection, verification, and the next iteration}

\paragraph{Confidence-gated comparison.}
A comparison is accepted when
\begin{equation}
 a_{ij}=\mathbf{1}\{c_{ij}\geq\tau\},\qquad \tau=0.7.
 \label{eq:gate}
\end{equation}
The gate determines whether a preference is strong enough to eliminate a candidate. Low-confidence candidates remain eligible for further comparison, allowing the controller to defer elimination when the predictor is uncertain.

The released tournament compares adjacent active candidates, with a bye for an unpaired candidate \citep{foreagentcode}. Confident winners advance, while inconclusive pairs enter a pending list. Pending candidates are compared with randomly chosen advanced candidates. A pending winner or another inconclusive outcome allows that candidate to advance, and its already-advanced opponent retains its place. If no candidate has advanced, a pending candidate is promoted directly. The tournament stops at one survivor or when the round count exceeds $2m$. The final ordering prioritizes survivors, then wins and later rounds; candidates can share a displayed rank.

\paragraph{Allocating executions.}
With $k=1$, candidates in the highest displayed rank group are eligible for execution. The released implementation applies an independent execution probability of 0.2 to each eligible candidate. If none is selected, it executes the first rank-0 candidate as a mandatory fallback. Consequently, every completed improvement batch receives execution feedback, and ties can result in multiple executions \citep{foreagentcode}.

\paragraph{Closing the feedback loop.}
Selected programs run their training and validation procedures in the execution environment. Their outputs are parsed into errors, execution status, and validation scores, which are stored in the journal. A failed execution can become the parent of a debugging attempt; a successful solution can become a parent for further improvement. Skipped candidates retain records without measured outcomes. The next iteration uses this updated history to choose its operation, select a parent, and generate new code. Search continues until the budget is exhausted, after which the agent returns the solution chosen by its internal validation criterion.

\subsection{Adaptive behavior and fixed harness components}

Execution feedback changes candidate code, available parent solutions, and the historical context supplied to the LLM. The comparison prompt, confidence threshold, tournament procedure, and execution policy remain predefined. This distinction identifies the proposed project's intervention: use experience to update the procedures that govern future search. The modules also interact through feedback availability. Generator changes alter the candidates presented to the selector, and selector changes alter which candidates produce measured outcomes. Harness evolution can therefore target individual modules and their coordination across iterations.

The original evaluation compares ForeAgent with AIDE on five MLE-bench tasks, using three runs per task and a 12-hour limit \citep{zheng2026predict,chan2024mle}.

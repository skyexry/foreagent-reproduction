# Introduction

Large language model (LLM) agents can write, run, debug, and refine machine learning programs. In systems such as AIDE, each executed program becomes a node in a search tree, and its validation feedback guides subsequent changes ([Jiang et al., 2025](https://arxiv.org/abs/2502.13138)). This loop is useful, but training and evaluating a candidate can consume a substantial share of an agent's compute budget. When several plausible modifications compete for the same GPU and wall-clock time, the agent must decide which ones deserve execution. A poor decision can spend the budget on weak programs or discard a promising one before its quality is observed.

This project asks: **Under a fixed GPU and wall-clock budget, can an ML agent improve its predictions of candidate programs' actual performance and use those judgments to allocate execution opportunities, ultimately producing a better final solution?** The research topic is the link between *pre-execution judgment* and *budgeted action*. The agent must judge candidates with incomplete evidence, then spend its limited execution time on the programs most likely to improve the final result. We will compare methods under the same task, candidate-generation setting, hardware, and time limit. Pairwise prediction quality and candidate-selection quality can be assessed using recorded outcomes; final program quality under the shared time budget requires an end-to-end run. This distinction makes it possible to see whether a more accurate judgment changes the agent's actual decisions.

Current systems approach this problem from two directions. AIDE uses real execution feedback to steer code search, obtaining direct evidence at the cost of running programs. ForeAgent inserts a **Predict-then-Verify** step into AIDE's improvement stage: it generates several candidate programs, uses an LLM to compare them with the task description and a data analysis report, and executes candidates favored by a confidence-gated selection procedure ([Zheng et al., 2026](https://aclanthology.org/2026.acl-long.182/)). In ForeAgent's published preference corpus, DeepSeek-V3.2-Thinking identifies the better program in **61.5%** of 18,438 pairs across 26 tasks (Table 2). Yet its five-candidate ranking study reports **31.1%** top-one accuracy (Table 3). These results show both the value of pre-execution signals and the difficulty of turning individual comparisons into a reliable choice among multiple programs. Our proposed research builds on this gap: improve the evidence used to judge candidate quality and test whether those improved judgments lead to stronger final solutions within the same execution time.

# Baseline Explanation

## Problem formulation and notation

ForeAgent is the representative baseline because it already combines an LLM's pre-execution judgments with code generation, tool-based execution, and feedback. Let $I$ be a machine learning task description, $D$ its dataset, and $C\in\mathcal C$ a candidate program. Let $u(C;I,D)$ denote the task's final evaluation score after orienting every metric so that larger is better; for a minimized loss, $u$ is the negative loss. The ideal objective is $C^*\in\arg\max_{C\in\mathcal C}u(C;I,D)$. The agent observes a candidate's measured performance only after running its training and evaluation code. At decision time, it instead receives the task description, a textual data report $D_{\mathrm{rep}}$, and candidate code ([Zheng et al., 2026, Sections 2–3](https://aclanthology.org/2026.acl-long.182/)). The true final score is reserved for evaluation of the decision.

For two candidates $C_i$ and $C_j$, the pretrained comparison model returns

$$
(z_{ij},\hat y_{ij},c_{ij})
=f_\theta(I,D_{\mathrm{rep}},C_i,C_j;P),
$$

where $P$ is the comparison prompt, $z_{ij}$ is the generated rationale, $\hat y_{ij}\in\{0,1\}$ selects an input position, and $c_{ij}\in[0,1]$ is self-reported confidence. The index refers to the order in which the two programs are shown. A comparison therefore gives a *relative judgment*, while the agent's final objective concerns the best actually executed program. The paper's offline metric is pairwise accuracy against the better recorded outcome; its end-to-end metric is the final task score, reported as Beat Ratio on the five-task benchmark (Tables 2 and 13).

## Architecture and information flow

ForeAgent retains AIDE's tree search over program nodes. AIDE drafts an initial solution, executes it, inspects errors and validation feedback, and then chooses whether to draft, debug, or improve a node. ForeAgent changes the **improvement** branch. Starting from an executed parent, it proposes $m=10$ distinct improvements, compares candidate code before training, ranks the candidates, and sends the selected candidate for actual execution. Runtime and validation feedback then return to the search tree for later decisions ([Zheng et al., 2026, Section 6.2](https://aclanthology.org/2026.acl-long.182/); [released agent implementation](../phase1-reproduction/code/author/mle-bench/agents/aide/aide/agent.py)). This keeps the agent's prediction connected to an environment that can verify it.

The data report supplies dataset context for those comparisons. In the paper's **Profile–Verify–Verbalize** pipeline, an LLM writes a profiling script, the script runs on the task data, an expert checks the execution log, and another LLM turns the observed statistics into a concise account of their modeling implications. The comparison prompt presents this report alongside the task description and two candidate programs, asking for a reasoned prediction of which will perform better. The report is evidence available *before* candidate training; it is distinct from either candidate's hidden evaluation outcome ([Zheng et al., 2026, Section 3.4 and Figures 14–16](https://aclanthology.org/2026.acl-long.182/)).

## Inference-time decision and execution rules

ForeAgent uses a pretrained LLM at inference time. Its candidate judge has **no newly fitted parameters or training loss** in this baseline; the operative rules are the comparison prompt, the confidence gate, the tournament, and the execution policy. A pairwise result is decisive when $c_{ij}\geq\tau$, with $\tau=0.7$ in the published ForeAgent configuration. Above this threshold, the predicted winner advances and the loser is eliminated. A lower-confidence result leaves the pair unresolved. The threshold is applied to the model's reported confidence, which is a decision signal rather than a measured candidate score ([paper, Section 6.2](https://aclanthology.org/2026.acl-long.182/); [released configuration](../phase1-reproduction/code/author/mle-bench/agents/aide/config.yaml)).

The [released tournament implementation](../phase1-reproduction/code/author/mle-bench/agents/aide/aide/world_model.py) makes this rule concrete. Each round compares adjacent active candidates, with an odd candidate advancing by a bye. Candidates from unresolved pairs enter a pending group. Each pending candidate is compared with a randomly chosen candidate that has already advanced; a confident loss eliminates it, while a confident win or another unresolved judgment lets it continue. The loop ends with one survivor or after its safety limit of more than $2m$ rounds. The code orders candidates by survival, win count, and round reached, then assigns displayed ranks; candidates with matching win-count and round metadata can share a rank. These tournament and tie details come from the author-released code, beyond the paper's three-stage summary.

The paper describes selecting Top-$k$ candidates, with $k=1$ by default. In the released [execution policy](../phase1-reproduction/code/author/mle-bench/agents/aide/aide/agent.py), candidates whose displayed rank is below $k$ are eligible for execution, each subject to a configured probability $p_{\mathrm{exec}}=0.2$. When every eligible candidate is skipped, the code executes the first rank-zero candidate as a fallback. Rank ties can therefore permit more than one execution in an improvement step. Executed nodes supply measured feedback; skipped nodes remain recorded without a measured metric. The probability and fallback are implementation details supplied by the [author configuration](../phase1-reproduction/code/author/mle-bench/agents/aide/config.yaml) and code.

ForeAgent's published evaluation provides two reference points for this proposal. Its **61.5%** pairwise accuracy establishes a useful but imperfect prediction signal on the fixed corpus. Under a 12-hour limit and three runs on each of five MLE-bench tasks, its mean Beat Ratio is **0.739**, compared with **0.695** for AIDE (Table 13): an absolute difference of **0.044**, or about **4.4 percentage points**. These are the authors' reported results. Our comparison will assess whether a stronger judgment and execution-allocation procedure improves the final solution under the same hardware and wall-clock limit, while also recording GPU use, prediction calls, and the quality of the selected candidates.

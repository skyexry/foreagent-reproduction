# 一页结论｜ForeAgent 哪个环节最值得改？

**研究目标是在给定的时间和算力下，让 Agent 最终交出执行成绩更好的代码。** 原版已冻结，修正版 C0 可作参考。现有离线接口专门支持“比较谁、何时停”，这让一项实验容易开展；整条 Agent 流程的优化重点仍开放。

| 环节 | 已有线索 | 怎样分辨它是否值得优化 |
|---|---|---|
| 生成候选代码 | 作者系统每次改进可提议10份代码，后续提案可以看到之前的计划。在线日志只给实际执行的候选提供成绩。[源码与覆盖表](baseline.md) | 先按同一轮查看方案是否重复、用了哪些不同思路、哪些得到执行。要判断改变生成方式是否有用，需让两种生成方式获得相同的执行机会，再比较能产生多好的候选。 |
| 让模型判断两份代码 | 已存判断里，模型自报高信心时也会判错。报告内容、候选差距及任务构成都可能影响结果。[信心与执行结果](../../reports/reproducibility-audit-20261108/evidence/confidence.json) | 看哪些错判涉及执行成绩差距大的候选。若要归因给提示或数据报告，需固定同一批代码，只改输入，另取判断。 |
| 决定比较谁、何时停 | 主动补问相对同条件随机补问的平均选择损失高0.01395，95%任务簇区间为[−0.01354, +0.05147]。850场的起始比较逐场相同。[先导结果](../../experiments/clean-ranking-v1/results/summary.json) | **D1 已完成这一环节的首项诊断。** 从同一起点比较“就停、主动多问、随机多问”，用历史执行分数衡量纠正与错改。它可以查明一次补问的价值，尚待比较的还有其他环节。 |
| 根据多场比较选出最终候选 | 实验用的胜率汇总会考虑有效对手数并保留并列。C0 使用原淘汰赛。两个选择流程的总分同时受选边和汇总影响。[模块卡](../modules.md) | 固定完全相同的已问对局和胜负，只换最终选取规则。若同一批证据经不同规则选出执行成绩明显不同的代码，就有研究汇总器的依据。改汇总器需另立环境版本。 |
| 决定何时真正运行代码、相信哪次验证 | 短测试里，部分候选自报的验证误差与统一重算口径有差异。C0 已修正最佳节点与提交文件的绑定。[短测与受控对照](../../experiments/clean-ranking-v1/先读结果.md) | 先分清模型判错、验证打分失真、执行预算花在了哪一步。评估新的执行安排时，要比较同等总时间下最终提交的成绩，并保留耗时、重试与失败。 |

**后续结果。** 静态加权训练先导已经结束。当前优先研究固定 corpus 上的离线候选选择。[离线方案与结果](../离线候选选择.md) · [训练结果](../../experiments/trajectory-weighted-judge-v1/README.md)

**第一轮实验记录。** 首轮 D1 和并行的裁判方向诊断 J1 已完成。D1 保留 C0；J1 纠正已问边的错判降低了平均损失，同时有73场变差。下一步建议先区分有效比较覆盖与汇总，再决定优化方向。[两项结果与案例](../../experiments/selection-frontier-01/README.md)

**跨模块比较的依据。** 先沿已保存的失败与成功案例，记录各环节能解释哪些成绩损失、哪些有替代解释，以及判清它还缺什么最小对照。优先选择对最终成绩或资源影响大、证据可信、能用合理成本验证的问题。26 个离线任务都是开发数据；历史池中最好的代码可衡量“已有好代码是否被选中”，评价生成能力还需比较不同生成方式产出的代码。
